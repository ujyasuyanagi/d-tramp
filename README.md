# D-Tramp — микросервисный карпулинг (курсовая, ИКБО-13-24, Дидоренко)

> «D-Tramp — Попутчик найдётся — дорога начнётся». Сервис совместных поездок: пользователи ищут попутки,
> бронируют места и вызывают виртуального водителя с карты.

Бэкенд собран как monorepo с npm workspaces: четыре самостоятельных сервиса + единый
GraphQL-шлюз, поверх — SPA на Vue 3. Стек: Node.js 22, TypeScript, Vue 3 + Vite, Leaflet
(тайлы Яндекс.Карт), Apollo Server 4 (GraphQL), MongoDB (mongoose), Docker Compose.

## Архитектура

```
                 ┌─────────────────────────┐
   браузер ─────►│  web  :8080 (nginx)     │  SPA + прокси /graphql в шлюз
                 └────────────┬────────────┘
                              │
                 ┌────────────▼────────────┐
                 │  api-gateway  :4000     │  единая точка входа, GraphQL, проверка JWT
                 │  (Apollo Server)         │
                 └───────┬──────┬──────┬────┘
                         │REST  │      │
              ┌──────────▼─┐ ┌──▼───────────┐ ┌──▼─────────────┐
              │user-service│ │ trip-service │ │  map-service   │
              │   :4001    │ │    :4002     │ │     :4003      │
              └──────┬─────┘ └──────┬───────┘ └──────┬─────────┘
                     └──────────────┴─── MongoDB ────┘
                          (общий кластер mongo:7,
                           коллекции по сервисам)

   map-service ──REST──► osrm :5002   дороги Москвы (граф в ./osrm-data); без него всё едет по прямой
```

* **api-gateway** — только GraphQL и авторизация; сам ничего не хранит, проксирует в сервисы
  и батчит обращения (DataLoader), чтобы список поездок не превращался в N запросов.
* **user-service** — регистрация/вход (bcrypt + JWT), профили водителя и пассажира.
* **trip-service** — поездки, поиск, брони с атомарным списанием мест.
* **map-service** — виртуальные водители: спавн вокруг точки пользователя, движение по реальным
  дорогам (OSRM), генерация госномеров по распределению регионов, вызов машины с маршрутом.
* **osrm** — self-hosted OSRM с графиком дорог Москвы: даёт расстояние, время и геометрию улиц
  (см. «Дороги и маршруты»). Факультативен: без него map-service работает по прямым.
* **web** — SPA (Vue 3 + Vite): карта с водителями, поиск попутек, брони, вызов машины;
  в проде отдаётся nginx'ом и проксирует `/graphql` — клиент говорит только в свой origin.
* **packages/shared** — JWT, JSON-клиент сервисов, валидация, логгер, geo-хелперы.

Внутренние сервисы — REST/JSON, доступны только внутри docker-сети `dtramp`;
публичная поверхность одна: `POST http://localhost:4000/graphql`.

## Запуск

```bash
cp .env.example .env        # compose подставит значения в контейнеры
scripts/osrm-prepare-pbf.sh # один раз: дороги Москвы и МО из PBF Geofabrik (нужен интернет)
docker compose up -d --build
docker compose ps           # все сервисы должны быть healthy
curl -s http://localhost:4000/health
```

Первый запуск `osrm` строит граф, если в `osrm-data` его ещё нет (на регионе — ≈2.5 мин и
1.5 ГБ RAM, на маленьком Overpass-графе ≈1 мин и 300 МБ), дальше контейнер просто поднимает
готовый. Скрипт подготовки дорог можно пропустить — тогда водители поедут по прямой.
`scripts/osrm-prepare.sh` — тот же результат для одного города через Overpass, без 800-мегабайтной
выгрузки округа.

Открыть интерфейс: <http://localhost:8080/>. Песочница GraphQL: <http://localhost:4000/graphql>.

Локальная разработка (Mongo из compose, сервисы — через tsx с перезапуском):

```bash
docker compose up -d mongo
npm install
npm run dev          # user-service, trip-service, map-service, api-gateway
npm run dev:web      # Vite на :5173, прокси /graphql → localhost:4000
npm run typecheck    # tsc --noEmit по всем workspace
node scripts/smoke.mjs
```

## Смоук-тест

`scripts/smoke.mjs` прогоняет сценарий целиком через шлюз и печатает `✓/✗` по каждому шагу:
auth (регистрация, дубликат, неверный пароль, `me` без токена), поездки и брони
(поиск без авторизации, списание мест, «Недостаточно свободных мест», видимость броней только
водителю поездки, возврат мест при отмене), карта (формат номеров, сортировка по расстоянию,
доля «местных» регионов, вызов машины, отмена чужого заказа, «водители стоят на дорогах» и
«поездка проложена по дорогам» — длина маршрута больше прямого расстояния) и гонка за последнее
место из трёх параллельных запросов, согласованность traffic-полей заказа). Итог — 45 проверок
(42 без OSRM); ненулевой exit code при провале. Три «дорожные» проверки сами отключаются, если
OSRM не отвечает: фолбэк на прямую — тоже штатный режим.
Отдельно проверяется длина поездки: `createTrip` считает километры по дорогам, а не линейкой
между точками, поэтому поездка Москва → Тверь выходит 183 км, а не 161.

## CI (Jenkins)

`Jenkinsfile` — declarative pipeline: `npm ci` → `npm run typecheck` → сборка образов →
подъём изолированного стека → smoke внутри `api-gateway`. CI не пересекается с рабочим стеком:

* отдельный compose-проект `dtramp-ci` и отдельный volume Mongo;
* host-порты 27018, 4100–4103, 8180 (рабочие 27017, 4000–4003, 8080 не затрагиваются);
* OSRM не запускается (`OSRM_URL=''`, режим `off`): граф в git не хранится, а три «дорожные»
  проверки smoke при этом сами пропускаются;
* smoke выполняется внутри контейнера `api-gateway` — Node на хосте и проброс портов не нужны;
* `post always` сохраняет `ci-artifacts/*.log` и делает `docker compose -p dtramp-ci down -v`.

Локальный Jenkins (Docker, только для этой машины):

```bash
cd ci/jenkins
docker compose up -d --build
# UI: http://127.0.0.1:8081 — admin / dtramp-ci (переопределяется JENKINS_ADMIN_PASSWORD)
```

JCasC при старте создаёт job `d-tramp-ci` из `Jenkinsfile`: репозиторий смонтирован в
`/workspace`, git клонирует его через `file://`. Job берёт ветку `main`, поэтому перед первым
запуском нужен хотя бы один коммит. Запуск — «Build Now» или через API:

```bash
crumb=$(curl -s -c /tmp/j -u admin:dtramp-ci http://127.0.0.1:8081/crumbIssuer/api/json | jq -r .crumb)
curl -s -b /tmp/j -u admin:dtramp-ci -H "Jenkins-Crumb: $crumb" \
  -X POST http://127.0.0.1:8081/job/d-tramp-ci/build
```

Контейнер получает `/var/run/docker.sock` и работает от root — это эквивалент root на хосте.
Порт слушает только `127.0.0.1`; не публиковать Jenkins наружу.

## Интерфейс (services/web)

Vue 3 (`<script setup>`) + Vite, состояние — реактивный store в `src/store.ts` (без Pinia:
данных мало, а лишняя абстракция только мешает читать). Единственная точка обращения к
бэкенду — `src/api.ts` (типизированный GraphQL-клиент, ошибки шлюза отдаются русским текстом).

* **Карта** (`components/MapView.vue`) — Leaflet + растровые тайлы Яндекса
  (`core-renderer-tiles.maps.yandex.net`), без API-ключа и без OpenStreetMap: OSM в этом
  окружении подвисает, а Яндекс отвечает ~80 мс на тайл. Если тайлы перестают отдаваться,
  карта показывает баннер и продолжает работать схематично — маркеры, клик и заказы не зависят
  от загрузки подложки.
* **Водители** — опрос `driversNear` раз в 1 с; маркеры не пересоздаются, а сверяются по id,
  поэтому симуляция движения выглядит плавно. Между ответами сервера позицию ведёт
  `requestAnimationFrame`: маркер линейно скользит от последнего показанного положения к новому
  (прыжок больше 1.5 км — не движение, а смена цели или респаун, такой ставится сразу).
  Для карты запрашивается ещё и круг видимой области (`map.getBounds()`, потолок 150 км): парк
  живёт по городам, и машины за краем экрана в ответе не нужны. Машины вне круга поиска
  приглушены и в список «Машины рядом» не попадают. Номер виден в подсказке маркера и в попапе.
* **Точки** — режим выбора цели (`pickTarget`) включает crosshair и клик по карте; одинаково для
  всех четырёх: «Откуда» и «Куда» в вызове машины (`rideFrom`/`rideDest`) и from/to при публикации
  поездки. Плюс посадку можно перетащить за пин и поставить кнопкой «Где я» (`navigator.geolocation`
  → точка посадки + карта подъезжает туда и приближается до z13; отказ — сообщение в баннер, а не
  молчание). Раньше посадка двигалась только перетаскиванием пина: дефолт — центр Москвы, и
  пассажиру из Химок пришлось бы тащить её через весь экран.
* **Маршрут заказа** — сплошная бирюзовая полилиния по вершинам `ride.path` (то есть по улицам),
  при появлении заказа вид подгоняется `fitBounds`, дальше картой правит пользователь.
  Линия показывает только остаток пути: голова — текущая позиция водителя (берётся из того же
  опроса парка по `ride.driverId`), а съеденные машиной улицы позади не рисуются. Индекс
  пройденной вершины (`remainingAlong` в `MapView.vue`) растёт только вперёд: иначе дрожь
  координат заставила бы линию то отрастать, то укорачиваться; если водителя нет в ответе
  (ушёл за круг обзора) — съеденный кусок всё равно не возвращается. Вершину при этом съедаем
  только когда машина её действительно проехала (проекция падает внутрь сегмента): без этого
  проверка «индекс растёт» съедала бы по вершине на каждый опрос — ≈200 км/ч против ≈50 км/ч
  водителя — и голова линии отрывалась от машины косой прямой через кварталы.
* **Предпросмотр маршрута** — серым пунктиром между точками «откуда/куда» до вызова машины
  ложится та же дорожная геометрия (`roadRoute` → `state.preview`), что потом уйдёт в заказ и в
  длину поездки; километры в панели подписываются «по дорогам» или «по прямой», так что режим
  маршрутизации виден пользователю, а не спрятан в фолбэке. Прямая остаётся и когда `map-service`
  молчит: публикация поездки не должна падать из-за профиля дорог.
* **Панели** — `AuthPanel` (вход/регистрация), `TripsPanel` (поиск, карточки поездок, публикация),
  `RidePanel` (радиус поиска, ближайшая свободная машина, вызов и статус заказа с ETA и ценой),
  `MyPanel` (брони, свои поездки, активные заказы).
* **Оформление** — чёрно-бело-синяя палитра, светлая и тёмная темы. Первый запуск учитывает
  `prefers-color-scheme`, ручной выбор хранится в `dtramp.theme`. На компьютере поиск расположен
  в плавающей панели слева от карты; на телефоне до 760 px — в нижней панели с тремя положениями.
  Панель переключается свайпом за ручку или нажатием на неё, при выборе точки сворачивается.
  Авторизация открывается в модальном окне кнопкой «Войти» или при бронировании гостем;
  выбранная поездка сохраняется и после входа требует явного подтверждения брони.
* **Сборка** — `vite build` → статика в nginx (`services/web/Dockerfile`), `/graphql`
  проксируется на шлюз через DNS Docker c `resolver 127.0.0.11` и переменной `proxy_pass`,
  чтобы 502 не появлялся после перезапуска `api-gateway`.

Важная мелочь: Leaflet сам навешивает классы на контейнер, поэтому `:class` на этом элементе
Vue перезаписывает `className` и «съедает» `leaflet-container` — класс режима выбора точки висит
на родительской `.map-wrap`.

И вторая, из-за которой машины «ехали не по дорогам» при идеальных данных: тайлы
`core-renderer-tiles` разложены в эллипсоидальном Меркаторе (EPSG:3397 ≈ EPSG:3395), а Leaflet
по умолчанию работает в сферическом (3857). Широта одна и та же, номер строки тайла — разный:
над Москвой расхождение выходит ~14 км, и маркеры, которые в базе стоят на дорогах, на экране
уезжали в подмосковные поля. Лечится опцией карты `crs: L.CRS.EPSG3395` — тогда тайлы, маркеры
и полилиния маршрута живут в одной системе координат.

## Тестовые данные и карточка машины

Клик по машине на карте открывает сведения о водителе и автомобиле: справа на ПК,
поверх карты на телефоне. Статус и расстояние обновляются вместе с опросом парка;
при выходе машины из области карты карточка отмечает, что показывает последние данные.
Фотографии моделей берутся из `assets/`, соответствие хранится в `services/web/src/carPhotos.ts`.
Для моделей без фотографии, включая Ford Focus, показывается заглушка.

Старые аккаунты «Иван Водителев» из smoke-теста и их поездки удаляются командой
`npm run cleanup:smoke-driver` (MongoDB на `127.0.0.1:27017/dtramp`, другой адрес — через
`MONGO_URL`). Скрипт ограничен именем и тестовым адресом `driver<число>@dtramp.test`;
для просмотра количества записей без удаления: `npm run cleanup:smoke-driver -- --dry-run`.
Новые smoke-прогоны снимают созданные поездки с публикации в `finally`; UI-проверка создаёт
и снимает с публикации собственную поездку, без зависимости от остатков smoke-теста.

`node scripts/driver-panel-check.mjs` проверяет рендеринг настоящего Vue-компонента с
тестовыми данными без браузера и сетевых соединений: выбор машины, обновление информации,
состояние вне области карты, закрытие, отсутствие фото и соответствие всех файлов `assets/`.

## Проверка интерфейса

`npm run build -w services/web && node scripts/redesign-check.mjs` проверяет редизайн на
собранном фронтенде без бэкенда: использует тестовые GraphQL-ответы и Chrome через pipe CDP.
Проверки охватывают темы, обмен городов, вход из бронирования, подтверждение брони,
мобильную панель и выбор точки, размеры от 320 до 1440 px, пустую выдачу и вкладку «Мои».
Скриншоты сохраняются в `docs/screenshots/redesign-*.png`. Для запуска нужны разрешённый запуск
Chrome и его системные вызовы; путь к бинарнику можно задать переменной `CHROME`.
Это отдельная проверка интерфейса; живой бэкенд проверяет сценарий ниже.


`node scripts/ui-check.mjs` поднимает headless Chrome (chrome-headless-shell из кэша Playwright),
управляет им по DevTools Protocol и прогоняет путь пользователя: карта и тайлы → водители →
плавность хода (на z15 считает разные позиции маркера между опросами — dead-reckoning обязан
дать десятки, а не один прыжок за опрос) → проекция (сверяет номер строки тайла под маркером
посадки с формулой EPSG:3395) → поиск попутки → регистрация → бронь → точка посадки и назначения
кликом по карте (обе — через `data-pick`/`data-field` панели) → предпросмотр линии (серый пунктир
обязан изгибаться по улицам и панель должна подписывать километры «по дорогам») → вызов машины →
полилиния маршрута (считает вершины в SVG — прямая от точки до точки это ровно два конца, у
городского маршрута их десятки) → голова зелёной линии у своей машины и её же длина через 25 с →
вкладка «Мои». Итог — 19 проверок. Перед прогоном скрипт чистит `localStorage`: профиль
headless Chrome переживает запуск, иначе «гость» на скриншотах — это пользователь прошлого
прогона, который уже всё забронировал. Каждый шаг печатается `✓/✗`, скриншоты складываются в
`docs/screenshots/`, ошибки консоли/исключения страницы выводятся в конце, exit code ненулевой
при провале.

```bash
docker compose up -d web && node scripts/ui-check.mjs            # прод-сборка на :8080
APP_URL=http://localhost:5173/ node scripts/ui-check.mjs         # против Vite
```

## GraphQL: основные операции

```graphql
# гость ищет попутку
query {
  trips(to: "Тверь", date: "2026-11-02", seats: 2, limit: 10) {
    id dateTime price seatsAvailable distanceKm
    from { name lat lon } to { name lat lon }
    driver { id name rating role }
  }
}

# водитель создаёт поездку (нужен Bearer-токен)
mutation ($input: CreateTripInput!) {
  createTrip(input: $input) { id status seatsAvailable }
}
# input: { from: {name:"Москва, Тверская", lat: 55.7602, lon: 37.6087},
#          to: {name:"Тверь", lat: 56.8587, lon: 35.9176},
#          dateTime: "2026-11-02T08:30:00.000Z", seats: 3, price: 900 }

mutation ($tripId: ID!) { bookTrip(tripId: $tripId, seats: 2) { id priceTotal status } }

# карта: машины рядом + вызов
query {
  driversNear(lat: 55.7558, lon: 37.6173, radiusKm: 3) {
    radiusKm
    drivers { id name status freeRide pricePerKm distanceKm car { model plate regionLabel } }
  }
}
mutation {
  requestRide(input: { pickup: {lat: 55.7602, lon: 37.6087}, dest: {lat: 55.6174, lon: 37.2613}, radiusKm: 5 }) {
    etaMin rideMinutes driver { name car { plate } } ride { id plate status price finishAt }
  }
}

# линия между точками — по улицам; там, где дорог в графе нет, byRoad: false и путь = отрезок
query {
  roadRoute(from: {lat: 55.7602, lon: 37.6087}, to: {lat: 56.8587, lon: 35.9176}) {
    byRoad distanceKm durationMin path { lat lon }
  }
}
```

Ошибки сервисов (401/403/404/409/400) возвращаются в `errors[].extensions.code` с оригинальным
русским сообщением, а не прячутся за `Internal server error`.

## Внутренние REST-эндпоинты

| Сервис | Метод | Назначение |
|---|---|---|
| user-service | `POST /register`, `POST /login` | выдача JWT |
| | `GET /me`, `PATCH /me` | профиль (Bearer) |
| | `GET /users/:id`, `POST /users/batch` | профили для шлюза |
| trip-service | `POST /trips`, `GET /trips`, `GET /trips/:id`, `GET /trips/mine`, `POST /trips/:id/cancel` | поездки и поиск |
| | `POST /trips/batch` | батчинг для DataLoader |
| | `POST /trips/:id/book`, `GET /bookings`, `POST /bookings/:id/cancel` | брони |
| map-service | `GET /drivers/near?lat&lon&radiusKm[&viewLat&viewLon&viewRadiusKm]` | водители рядом + парк в поле зрения |
| | `GET /road?fromLat&fromLon&toLat&toLon` | длина, время и геометрия линии между двумя точками |
| | `POST /rides`, `GET /rides`, `GET /rides/:id`, `POST /rides/:id/cancel` | вызов машины |
| | `GET /stats` | состав водителей по регионам и городам |
| osrm | `GET /route/v1/driving/…`, `GET /nearest/v1/driving/…` | маршруты по дорогам, посадка точки на улицу |
| api-gateway | `GET /health`, `POST /graphql` | точка входа |

## Виртуальные водители (map-service)

* **Парк по городам, а не в одной точке**: `CITY_SPAWNS` в `src/cities.ts` — 26 городов
  (Москва, 8 крупных городов Подмосковья, столицы и крупные города ЦФО), каждый со своей точкой,
  радиусом «дома» и весом. `MAP_DRIVER_COUNT` (90) делится между городами методом наибольшего
  остатка пропорционально весу, поэтому Москва получает ≈21 машину, Воронеж — 4, Смоленск/Курск/
  Тула — по 3. Внутри города места распределяются с убыванием к краю (`r = R·u`, т.е. ≈1/r —
  в центре гуще). Водитель «живёт» в своём `home`-городе: цели он выбирает там же, и в Тверь его
  не утаскивает. `MAP_CITIES` сужает список (ключи через `;` — `msk; tver`, или своя точка
  `54.196,37.618,71` с радиусом `MAP_ADHOC_RADIUS_KM`).
  Радиус поиска `MAP_RADIUS_KM` (3 км) — отдельное число: за пунктирным кругом на карте тоже видно
  машины, просто они приглушены и в заказ не берутся. Если вокруг точки поиска меньше
  `MAP_MIN_NEAR` (6) машин, дальние свободные перегоняются на дороги рядом — прообраз реального
  rebalancing автопарка. Перегон ограничен `REBALANCE_MAX_KM` (120 км) и ищет якорь в ближайшем
  городе парка: утаскивать смоленскую машину на улицы Воронежа смысла нет, там ещё нет дорог.
* **Обзор, а не вся карта**: круг поиска и круг обзора — разные вещи. Фронт после каждого
  `moveend` считает прямоугольник видимой части карты и просит `/drivers/near` с
  `viewLat/viewLon/viewRadiusKm` (потолок 150 км). Сервис возвращает union: машины внутри круга
  поиска (для панели и заказа) плюс всё, что попало в поле зрения (для карты), и `distanceKm`
  считается от центра поиска у всех, поэтому фильтр панели не съезжает. Следить за парком на всей
  карте России незачем — если пользователь смотрит на Воронеж, тянем Воронеж.
* **Движение**: тик `SIM_TICK_MS` (0.5 с), водитель едет к случайной цели со своей скоростью
  (28–68 км/ч); при OSRM цель берётся на дороге, а путь — полилиния улиц (вершины «съедаются»
  бюджетом километров за тик), без него — дуга по большой окружности (haversine + пеленг).
  Часть машин в моменте `busy`, освобождается по таймауту; `free`-водители периодически
  уезжают на заказ, а вероятность уезда нормируется на секунду, а не на тик: иначе при ускорении
  тика парк за минуту весь уходит в `busy`. Состояние живёт в памяти, в MongoDB каждые 4 тика —
  снапшот состава.
* **Госномера** (`src/plates.ts`): формат `Х###ХХ###`, буквы только из `АВЕКМНОРСТУХ`,
  код региона — с ведущими нулями («077»). Регион номера берётся из `home`-города машины, поэтому
  у воронежских машин 36/136, у тульских — 71, а не московские коды на всех. Внутри региона
  выбор взвешенный: Москва (77) даёт ≈58 % московских кодов (77/97/99/177/777/797/997),
  ≈18 % Подмосковья (50/90/150/190/750) и редкие дальние соседи по ~1–2 %; у каждой столицы ЦФО
  своя таблица соседей (Тверь 69 тяготеет к Москве, Воронеж 36 — к области).
* **Детерминированность**: генератор — mulberry32 с seed (`MAP_SEED`), чтобы состав машин
  и скриншоты можно было воспроизвести.
* **Adapter**: `src/driver-source.ts` описывает интерфейс `DriverSource`
  (`listNear`, `nearestFree`, `acquire`, `release`, `stats`). Маршруты и шлюз знают только его;
  реальный источник (API карт, приложение водителя) подключается в `createDriverSource()`
  через `DRIVER_SOURCE`, без правок остальных сервисов.
* **Вызов машины**: свободный водитель резервируется под заказ (`acquire` с id заказа),
  маршрут «водитель → посадка → назначение» считается целиком и делится на ноги: подача и поездка.
  Оттуда — ETA подачи, время в пути и цена `pricePerKm × расстояние по дороге` (0 при акции
  `freeRide`); по истечении `finishAt` заказ становится `completed`, а водитель — свободным.
* **Пробки при выборе машины** (`src/traffic.ts`): из растрового слоя Яндекс.Карт (`l=trf` — тот же,
  что фронт показывает на карте) по пикселям вдоль маршрута OSRM оценивается обстановка на подаче
  каждой из ближайших машин. По умолчанию едет ближайшая; если она стоит в пробке, а другая машина
  чуть дальше приезжает заметно быстрее (≥ 1 мин), выбирается она. Пробки на подаче и в поездке
  считаются отдельно (маршрут режется по точке посадки), ETA подачи удлиняется на задержку, а в
  заказе сохраняются `trafficLevel`, `pickupDelayMin` и `trafficPreferred`. Слой кэшируется на 90 с;
  `MAP_TRAFFIC=off` выключает учёт, при недоступном слое всё работает по свободному потоку.

## Дороги и маршруты (OSRM)

Водители и заказы ездят по реальным улицам: self-hosted [OSRM](https://project-osrm.org/)
(`osrm/osrm-backend:v5.25.0`) с одним графиком дорог — Москва и область, коридор Москва → Тверь
и крупные города ЦФО отдельными островами. Это не обязательный
сервис — `src/router.ts` описывает профиль `RoadRouter` с режимами `osrm` и `off`; в `off` те же
расчёты честно идут по прямой, поэтому отсутствие OSRM не ломает ни демо, ни смоук-тест.

* **Данные и форма графа**: `scripts/osrm-prepare-pbf.sh` — путь, которым собран текущий граф.
  Качает PBF Geofabrik, режет `osmium extract`, оставляет дороги `osmium tags-filter
  w/highway r/type=restriction` (отношения ограничений поворота тащим вместе с дорогами, иначе
  граф разрешает развороты, которых на самом деле нет) и только затем отдаёт вход в
  `osrm-extract`. osmium живёт в контейнере (`services/osrm/osmium.Dockerfile`), на хосте ничего
  не ставится. Город — «остров», а не сплошное покрытие: `scripts/osrm-city-boxes.ts` берёт
  коробку коридора и по каждому городу из `CITY_SPAWNS` его `roadBbox` (радиус города + 6 км),
  отбрасывая боксы, которые уже лежат внутри коридора. Один `osmium extract` принимает один
  `--bbox` (флаг нельзя повторить, а `--config` с массивом extracts на 16 боксах сожрал 8 ГБ и
  был убит OOM-killer), поэтому боксы режутся по одному в `part-*.osm.pbf`, а потом сливаются
  `osmium merge` — он же выкидывает дубликаты узлов на границах коридора и городов. Числа прогона:
  882 МБ ЦФО, 16 боксов → 399 МБ обрезки → **93 МБ дорог (7.87M узлов, 1.56M путей, 35.9k
  отношений, 4.79M использованных рёбер)**, `check-refs` чист (потерянных узлов 0);
  extract 42 с (пик **1.80 ГБ RAM**) → partition 66 с (0.98 ГБ) → customize 8 с (0.83 ГБ),
  весь цикл 4м10с, артефакты **1.2 ГБ**. Без предварительной фильтрации тот
  же вход — 111.7M узлов, и сборка упирается в память машины.
* **Быстрый старт в другом городе**: `scripts/osrm-prepare.sh` выгружает дороги через Overpass
  (bbox `55.66,37.45,55.86,37.79`, ≈113 МБ OSM XML) в `osrm-data/<NAME>.osm`; свои `BBOX` и
  `NAME` — другой город. Overpass отдаёт только XML и считает медленно: измеренный тайл 0.25°×0.25°
  (≈28×18 км) — 132k дорог, 637k вершин, 16 МБ и **46 с** холодного запроса, а Московская область
  — сотни таких тайлов. Поэтому на регион идём не через скрейп, а через PBF.
* **Граница покрытия** видна в интерфейсе: вне дорог `byRoad: false`, километры считаются
  по прямой и подписаны «по прямой». Измерено на текущем графе: Москва → Тверь 183.9 км,
  Тверь → Химки 163.5 км, Москва → Рязань 195.8 км, Москва → Калуга 184.1 км, Калуга → Тверь
  340.1 км — по дорогам; внутригородские заказы Воронежа, Тулы, Калуги, Смоленска и Твери
  (6.8–14.1 км) — тоже по дорогам. Москва → Тула 173.4 км, Москва → Воронеж 466 км,
  Воронеж → Тула 300 км, Москва → Смоленск, → Орёл, → Ярославль — прямая: эти острова с
  коридором не пересекаются, OSRM отвечает `NoRoute`, и фронт честно рисует прямую. Новый регион =
  ещё один запуск `osrm-prepare-pbf.sh` с своим `BBOX` и `NAME` (но два датасета OSRM между
  собой не связываются, см. пункт ниже); связность внутри одного датасета появляется сама собой
  там, где боксы перекрываются — поэтому Рязань и Калуга «пришиты» к коридору.
* **Почему нельзя «просто покрыть всю Россию»**: Geofabrik отдаёт Россию по федеральным округам
  (`russia/central-fed-district-latest.osm.pbf` и ещё 9), суммарно **3.9 ГБ** pbf, один ЦФО —
  0.82 ГБ, и в нём уже **111.7M узлов / 12.7M путей**. Один датасет OSRM на всю страну — это
  порядка 20M узлов и 30M рёбер дорог, то есть 10–20 ГБ RAM только на `osrm-routed`, при 6 ГБ
  свободных на машине курсовой. Отдельные датасеты по округам тоже не решают: OSRM не умеет
  прокладывать маршрут между двумя своими базами, так что Москва → Казань осталась бы без дорог.
  Честная граница демо — регион, собранный в один связный граф, а за его пределами рабочий
  фолбэк на прямую с `byRoad: false`.
* **Сборка**: `services/osrm/init.sh` при первом старте прогоняет `osrm-extract -p car.lua` →
  `osrm-partition` → `osrm-customize` и запускает `osrm-routed --algorithm mld`; готовые
  артефакты переиспользует, имя графа берёт из `OSRM_MAP_NAME`. Имя диктует вход: `osrm-extract`
  не принимает `-o` и пишет `<имя-файла>.osrm`, поэтому `moscow-csfo-roads.osm.pbf` — это граф
  `moscow-csfo-roads`. На маленьком Overpass-графе (Москва в 4 боксах) сборка занимает ≈1 мин и
  300 МБ RAM, на текущем регионе — 4м10с и 1.80 ГБ (см. «Данные и форма графа»).
* **map-service**: `/route/v1/driving/…?overview=full&geometries=geojson` (ноги — подача и
  поездка), `/nearest` для посадки на дорогу; таймаут запроса 2.5 с, после трёх неудач подряд
  — cooldown 30 с и работа по прямой. `OSRM_URL` пусто → режим `off` сразу.
* **Страж правдоподобия** (`roadBetween` в `src/router.ts`): OSRM никогда не отвечает «таких дорог
  нет» — он тихо прилепит Тверь к улице в Химках, если граф собран по одной Москве, и вернёт 17 км
  вместо 180. Поэтому у ответа проверяются дрейф концов (≤ 2 км) и длина (≥ 0.98 прямой); всё, что
  не прошло, считается по прямой и помечается `byRoad: false`.
* **Длина поездки** тоже берётся с дорог: шлюз перед `createTrip` спрашивает `/road` и передаёт
  `distanceKm` в trip-service (сам trip-service с map-service не знакомится — у него остаётся
  haversine как фолбэк). Internal-эндпоинт `GET /road` и GraphQL `roadRoute` отдают одно и то же:
  геометрию, километры, минуты и флаг `byRoad`.
* **Геометрия у заказа** сохраняется в `Ride.routePath` (не чаще 150 вершин — `decimate`),
  отдаётся шлюзом как `Ride.path`, а фронт рисует по ней полилинию и подгоняет вид под маршрут.
* **Диагностика**: `mapStats.router` и `/health` map-service показывают `osrm` или `off`.
* **Если машины «едут мимо дорог» на глаз, а `/nearest` отвечает 0 м** — это не симуляция,
  а расхождение проекций тайлов и данных (см. `crs: L.CRS.EPSG3395` в разделе про интерфейс).
